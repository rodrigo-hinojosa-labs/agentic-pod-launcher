# Contrato AO: el oráculo del host (`tests/nightly-alert.bats`)

Qué prueba la suite del host (sin Docker ni red) y con qué instrumentos, de modo que un cambio que apague el aviso en silencio haga caer al menos un test. Un chequeo que no puede fallar no es evidencia (025, 039): por eso el oráculo trae sus propias guardias de no-vacuidad y una tabla de mutaciones (en `quickstart.md`).

## 1. El `gh` falso (`tests/fixtures/nightly-alert/gh`)

- Es un script bash que el test pone al frente del `PATH`; mantiene su estado en `$FAKE_GH_STATE` (variable obligatoria: sin ella sale con 99, para que un test no corra contra un estado fantasma).
- **Estado**: `issues.json` (arreglo de issues con `number`, `state` `OPEN|CLOSED`, `title`, `body`, `labels`, `assignees`, `comments`, `url`), `labels.txt` y `calls.log`. Un helper del test siembra issues con un marcador dado.
- **Lista blanca de banderas** (las verificadas en `gh` 2.102.0, research R8): `issue list --label --state --limit --json`; `issue create --title --label --assignee --body-file`; `issue comment --body-file`; `issue edit --body-file`; `issue reopen --comment`; `issue close --reason --comment`; `label create --color --description`. Cualquier otra bandera o subcomando sale con 64, escribe `UNSUPPORTED` en `calls.log` y hace fallar el test: el oráculo no puede aprobar un script que el `gh` real rechazaría.
- **`issue list --json`**: filtra por etiqueta y estado (`open|closed|all`), ordena por número descendente (más reciente primero), aplica `--limit` y proyecta solo los campos pedidos; sin `--jq` (el script filtra con `jq`).
- **Inyección de fallas**: `FAKE_GH_FAIL` con una lista separada por comas de `list`, `label`, `create`, `create_assignee` (falla solo si hay `--assignee`), `edit`, `comment`, `reopen`, `close`. Un comando que falla escribe un mensaje a `stderr`, sale con 1 y no cambia el estado.
- **`calls.log`**: una línea por llamada, `verbo<TAB>argumentos`; las mutantes son `create`, `edit`, `comment`, `reopen`, `close` y `label-create`.

## 2. El arnés

Ejecuta el script con un entorno explícito (las variables de `data-model.md` sección 1), `PATH=<directorio del falso>:$PATH`, en un directorio temporal (allí vive `e2e.tap`), con la disposición de SIGPIPE que pida `SIGPIPE_MODE`, fijada con `perl` justo antes de lanzarlo: `ignore` por defecto (es la que el script hereda en el runner de GitHub) o `default`. A diferencia de 039, donde el `docker` falso en bash necesitaba el valor por defecto para morir como el binario Go, aquí el script debe dar el mismo resultado con las dos, y N17 lo comprueba.

**Costuras de prueba** (el workflow no las define): `ALERT_SCRIPT` y `ALERT_WORKFLOW` apuntan a las rutas bajo prueba (por defecto `.github/scripts/nightly-alert.sh` y `.github/workflows/docker-e2e.yml` del repositorio), de modo que cada mutación se aplica a una copia sin tocar el árbol; `NIGHTLY_ALERT_NOW` fija el "ahora" del script (épocas del 20, 21 y 22-10-2026 a las 12:00 UTC: `1792497600`, `1792584000` y `1792670400`), así que ningún test depende del reloj ni de la medianoche UTC. Si el `gh` falso registró una llamada `UNSUPPORTED` (una que el `gh` real rechazaría), el propio arnés hace fallar el test que la provocó: el script la convierte en un `::warning::` y sale 0, así que sin esto ninguna aserción la vería. Los argumentos con forma `VAR=valor` van al entorno del script y los demás van al script tras el subcomando (`_alert simulate red`). Deja `status`, `output` y el estado del falso para las aserciones. Las afirmaciones negativas se escriben con `_lacks` o `run …; [ "$status" -ne 0 ]`, nunca con `!` intermedio (bats no lo convierte en falla); los `[[ ]]` intermedios se evitan (muertos en bash 3.2).

## 3. Guardias de no-vacuidad

1. Los casos "sin acción" no se contentan con la ausencia de llamadas mutantes: exigen además la anotación `::notice::nightly-alert:` en la salida (prueba que el script corrió y decidió) y, si correspondía leer, la llamada `list` en `calls.log`.
2. Si el script no existe o no es ejecutable, el primer test que lo invoca falla con un mensaje que lo dice.
3. Un autotest del falso: llamado directo, registra la llamada y rechaza una bandera desconocida (N00). N00 es la **calibración del instrumento**: su capacidad de fallar se demuestra rompiendo el falso una vez (por ejemplo, haciendo que acepte cualquier bandera) y anotándolo.
4. La tabla de mutaciones de `quickstart.md`: cada mutación se aplica a una copia del script o del workflow, el test cazador debe caer, y la copia se descarta.

## 5. Reglas de la ejecución

- Test-first: los tests se escriben y se ven en ROJO (script y workflow ausentes) antes de crear cualquiera de los dos.
- Gate dual de bash 3.2 y 5.x, secuencial, nunca concurrente; `shellcheck -S error -e SC1090,SC1091` con el comando exacto del job de CI sobre el árbol.
- Los casos de comportamiento no dependen del orden entre sí: cada uno crea su propio estado.

## 6. Enmienda 1: el oráculo del empuje por Telegram (N32 a N42)

Contrato que se verifica: `contracts/telegram-push.md`. Decisión y razones: `research.md` R23.

**Instrumentos nuevos** (en `tests/fixtures/nightly-alert/`):

- `tg-server.py`: servidor HTTP local de la biblioteca estándar de Python 3 (compatible con 3.9), en `127.0.0.1` y un puerto libre que escribe en `tg-port`. Registra cada petición en `tg-requests.jsonl` (ruta, token de la ruta, campos decodificados, tipo de contenido) y añade una línea `tg` a `events.log`; comprueba el token y el chat contra `tg-token` y `tg-chat`; responde según el modo de `tg-mode`: `ok` (200 `{"ok":true,...}`), `ok-false` (200 con `{"ok":false,...}`: el contrato exige mirar `ok` y no solo el código HTTP), `unauthorized` (401), `chat-not-found` (400), `rate-limit` (429 con `retry_after`), `server-error` (500 con cuerpo de texto), `echo-token` (400 cuya `description` cita la ruta de la petición, y con ella el token, precedida de 70 caracteres de relleno para que el token quede a caballo del corte de 120 caracteres del script) y `hang` (no responde). Un token mal formado da 404, como Telegram (M10).
- `curl`: espía que va delante del `curl` real en el `PATH` del arnés; anota sus argumentos en `curl-argv.log` (un encabezado `--- curl` y un argumento por línea) y delega en el real (busca el real en el `PATH` sin su propio directorio). Con `TG_SPY_FAIL=url` (y una llamada que empieza con `-K`) no toca la red: termina con el código 3 y una línea de error de `curl` que cita la URL de la configuración, token incluido, como lo hace `curl` con algunas URL mal formadas. Si la llamada empieza con `-K`, anota además `config-perms` con el modo del archivo y, si `TELEGRAM_BOT_TOKEN` o `TELEGRAM_CHAT_ID` siguen en su entorno, una línea `ENVLEAK`: son hechos del instante de la llamada, porque el archivo ya no existe cuando el script termina; la comprobación de entorno busca también el **valor** del token bajo cualquier nombre de variable (`export TG_TOKEN` pasaría la de nombres). Copia además la configuración recibida, con el token enmascarado, a `curl-conf.log` para que los tests lean el endpoint, el tope de tiempo y las opciones de la petición.
- El `gh` falso gana dos anotaciones: añade una línea `gh <verbo>` a `events.log` en cada llamada (para comprobar el orden entre el issue y el mensaje) y, si recibe `TELEGRAM_BOT_TOKEN` o `TELEGRAM_CHAT_ID` en su entorno, escribe `ENVLEAK` en `calls.log`. N00 (la calibración del `gh` falso) gana una aserción por cada anotación y se demuestra rompiendo el falso una vez por cada una. El falso busca también el valor del token en su entorno y gana tres costuras para los fallos que un `gh` real tiene además de fallar: `FAKE_GH_HANG` (lista de operaciones que nunca responden), `FAKE_GH_LIST=garbage` (`issue list` responde algo que no es una lista, con código 0) y `FAKE_GH_CREATE_OUT` (lo que `issue create` imprime en vez de la URL).

**Arnés**: `_tg_up` arranca el servidor, fija el token centinela (`987654321:SENTINELtokenSENTINELtoken0123456789a`, de formato válido) y el chat de prueba, y a partir de ahí `_alert` pasa al script `TELEGRAM_BOT_TOKEN`, `TELEGRAM_CHAT_ID`, `TELEGRAM_API_BASE` (el puerto local) y `TELEGRAM_MAX_TIME=3`; `teardown` mata el servidor. Sin `_tg_up` el script recibe los secretos vacíos (omisión con advertencia), de modo que los 32 tests anteriores no necesitan servidor; los dos que afirmaban "ninguna advertencia" ahora excluyen la de la omisión. Como el `UNSUPPORTED` del `gh` falso, un `ENVLEAK` hace fallar el test que lo provocó.
