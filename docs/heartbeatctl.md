# heartbeatctl — reference

CLI for inspecting, controlling, and mutating the in-container heartbeat. Image-baked at `/opt/agent-admin/scripts/heartbeatctl`, symlinked to `/usr/local/bin/heartbeatctl`.

Full subcommand list (as of v0.27.0, matches `docker/scripts/heartbeatctl` dispatch): `status`, `logs`, `show`, `test`, `pause`, `resume`, `reload`, `kick-channel`, `drop-plugin`, `set-interval`, `set-prompt`, `set-notifier`, `set-timeout`, `set-retries`, `backup-identity`, `backup-vault`, `backup-config`, `token-check`, `qmd-reindex`, `qmd-migrate`, `wiki-graph`, `help`. Since 0.32.0 (046) also `backup-memory`, `backup-history` and `backup-status`.

## Invocation

**Docker mode — always pass `-u agent` to docker exec.** The container runs with `cap_drop: ALL` + `no-new-privileges: true`, and several heartbeatctl paths (`reload`, `pause`, `set-*`) write to agent-owned files. The default `docker exec` is root, which cannot write those without `CAP_DAC_OVERRIDE` / `CAP_FOWNER`.

```bash
docker exec -u agent <agent-name> heartbeatctl <subcommand> [args]
# Inside the tmux session it's on PATH:
heartbeatctl <subcommand> [args]
# From the host, agentctl proxies any subcommand:
./scripts/agentctl heartbeat <subcommand> [args]
```

**Local mode (deployment.mode: local, features 011-013): there is no heartbeatctl binary on the host.** Only three actions have local equivalents, dispatched by `agentctl heartbeat <sub>` as direct execs of the rendered `scripts/local/agent-*.sh` wrappers (no `systemctl`, no polkit):

- `agentctl heartbeat qmd-reindex` — refuses `--dry-run` (the local entrypoint has none; it would run a real reindex).
- `agentctl heartbeat backup-vault` — passes `--dry-run` through.
- `agentctl heartbeat wiki-graph`

Every other `agentctl heartbeat <sub>` (including `token-check`) is docker-only and exits `2` in local mode. Local schedules run as systemd `OnCalendar` timers rendered from `modules/local-*.timer.tpl`, not cron — see the per-command notes below.

Local kill-switch: the rendered `scripts/local/agent-killswitch.sh` stops the main unit **and** every companion unit that carries the work documented here — `agent-<name>-qmd-reindex.timer`, `agent-<name>-qmd-watch.service`, `agent-<name>-vault-backup.timer`, `agent-<name>-wiki-graph.timer`, `agent-<name>-healthcheck.timer` (013 FR-008). Pass `--disable` to also prevent them starting at boot. Stopping only the main unit would leave the vault backup pushing to the fork long after you thought the agent was off.

## Read commands

### `status [--json]`

Dashboard. Reads `state.json` and enriches with live `crond.alive` / `pid` at read time.

Pretty output (no flag):

```
heartbeat: ENABLED
  interval: 2m   cron: */2 * * * *
  prompt:   Check status and report to notification telegram bot
  notifier: telegram
  last run: ok  @ 2026-04-19T19:36:00Z  (125000ms, attempt 1)
  counters: runs=2 ok=2 timeout=0 error=0 streak_fail=0  24h=100%
  crond:    alive (pid 16)
  updated:  2026-04-19T19:38:05Z

recent runs:
  2026-04-19T19:19:14Z  ok  73000ms   Check status and report...
  2026-04-19T19:36:00Z  ok  125000ms  Check status and report...
```

`--json`: emits `state.json` enriched with a live `.crond = {alive, pid}` overlay, re-serialized through `jq -c` — machine-parseable, but not byte-identical to the file (`state.json` itself always stores `crond: {alive: null, pid: null}`; the runner never knows crond's state).

Exit codes:

- `0` on success.
- `1` if `state.json` schema is unknown (refuses to guess at incompatible formats).
- `2` if `state.json` is missing (heartbeat has never run — try `heartbeatctl reload`).

### `logs [-n N] [--json]`

Tail `logs/runs.jsonl`. Default `N=20`.

Pretty output (no flag): a table of `TS | STATUS | DUR | ATTMPT | PROMPT[:60]`.

`--json`: emits raw JSON lines, one per run, piping-safe for `jq`.

### `show`

Dumps the three primary sources of truth so you can tell what's configured vs. what's staged:

- `heartbeat.conf` (shell-sourced by `heartbeat.sh`, regenerated by `reload`)
- the staging crontab (`scripts/heartbeat/.crontab.staging` — the *desired* schedule written by `reload`)
- `agent.yml` slice: `features.heartbeat` + `notifications`

Note `show` does **not** read `/etc/crontabs/agent` (what crond actually runs, root-owned). During the propagation window (~75s worst case, see "Propagation timing"), or if the sync loop is broken, the installed crontab can lag what `show` displays.

## Control commands

### `test [--prompt "..."]`

Run one heartbeat right now. Writes a line to `runs.jsonl` with `trigger: manual`. Counters are trigger-agnostic: a manual test updates `state.json` exactly like a cron tick — a failed test increments `counters.consecutive_failures` (and `total_runs`), a successful one resets the failure streak. `trigger: manual` is recorded in the run line only; the counter update never consults it.

Accepts `--prompt "override"` to test a different prompt without changing `agent.yml`.

Returns when the run completes — expect the typical duration (same as a cron tick).

### `pause`

Sets `features.heartbeat.enabled = false` in `agent.yml`, prefixes the crontab line with `# paused:`, and drops the cron dispatch. Idempotent — running it twice does not double-comment.

### `resume`

Inverse of `pause`. Sets `enabled = true`, uncomments the crontab line.

### `reload`

Re-reads `agent.yml`, regenerates `heartbeat.conf`, rewrites the crontab staging file, and ensures `logs/` exists. Does **not** signal crond (busybox crond dies on SIGHUP). crond picks up the new crontab on its own minute tick — propagation is described in the "Propagation timing" section below.

Idempotent. Called automatically by:

- `entrypoint.sh` on every container start (via `start_services.sh`).
- Every `pause` / `resume` / `set-*` subcommand after mutating `agent.yml`.

### `kick-channel`

Kills the `agent` tmux session; the `start_services.sh` watchdog respawns it within ~2s with a fresh plugin attachment. This is the manual recovery for the silent-stuck Telegram bridge case (bun alive and polling, but MCP channel notifications not reaching the session — automated detection was reverted for false positives). Exit `2` if tmux or the session is absent. Docker mode only (the tmux session lives in the container).

### `drop-plugin <spec>`

Removes a plugin spec (e.g. `caveman@JuliusBrussee`) from `agent.yml.plugins[]`. Idempotent (no-op with exit `0` if the spec isn't listed), atomic with `agent.yml.prev` backup/restore on `yq` failure. Does **not** auto-kick the channel — run `heartbeatctl kick-channel` afterwards so the next watchdog respawn consumes the new plugin list.

## Mutation commands

All mutations are transactional with automatic rollback on failure:

1. Validate the value. Reject with exit code 1 if invalid; `agent.yml` untouched.
2. Back up `agent.yml` to `agent.yml.prev`.
3. Apply the mutation via `yq -i`.
4. Run `reload`.
5. On any failure in steps 3–4, restore `agent.yml.prev` and re-run `reload` so the live state matches the backed-up config. Exit code 2.
6. On success, delete the backup.

### `set-interval <Nm|Nh>`

Accepts a restricted divisor table so the derived cron expression is always valid:

- `Nm` for `N` in `{1, 2, 3, 4, 5, 6, 10, 12, 15, 20, 30}` → `*/N * * * *` (or `* * * * *` for `1m`).
- `Nh` for `N` in `{1, 2, 3, 4, 6, 8, 12}` → `0 */N * * *` (or `0 * * * *` for `1h`).
- `24h` → `0 0 * * *` (once per day at 00:00 UTC).

Anything else is rejected. Examples that do NOT work: `30s`, `45m`, `7m`, `5h`, `2h30m`.

### `set-prompt "<str>"`

Updates `features.heartbeat.default_prompt`. Accepts the prompt as an arg or via stdin if no arg is given. Length 1..4000 chars.

Warns to stderr (but does not refuse) if the current `notifications.channel` is `telegram` and `.env` is missing `NOTIFY_BOT_TOKEN` / `NOTIFY_CHAT_ID`.

#### Prompt examples by use case

The default prompt (`Status check — return a short plain-text report (uptime, notable issues). No tool use; your stdout is forwarded verbatim to the notifier.`) is intentionally generic. Replace it via `heartbeatctl set-prompt "..."` to match what your agent actually does:

- **Cluster health** — *"List Kubernetes pods in CrashLoopBackOff or Error in the last 30m via `kubectl get pods -A`. Return only the failing pods with their namespace and reason. If everything is healthy, output `OK: N pods running`."*
- **Vault ingestion monitor** — *"Count `*.md` files under `~/.vault/wiki/` and compare against the last value in `~/.vault/log.md`. Report any drop or > 10% gain. Note any sync-conflict files in `~/.vault/`."*
- **Jira sprint blockers** — *"Use `mcp__atlassian__jira_search` to query the active sprint of project KEY. List blockers (status=Blocked or label=blocker). Group by assignee. Output one bullet per blocker with `[KEY-123] @user — title`."*
- **Log tailer** — *"Tail the last 50 lines of `/workspace/claude.log` and report any ERROR or WARN. Include timestamps and a one-line summary of patterns (e.g. `3× 'connection refused' between 14:05 and 14:18`)."*
- **Heartbeat-as-canary** — *"Reply with `pong @ <ISO timestamp>`. No tool use. This proves Claude Code is reachable and the notifier round-trip works."*

Each prompt should:
1. Be self-contained — heartbeat sessions run in an isolated `CLAUDE_CONFIG_DIR=/home/agent/.claude-heartbeat` with no plugins and no conversation history. Auth (`.credentials.json`) and `.claude.json` are symlinked from the interactive session's config dir; `settings.json` is rewritten with `enabledPlugins = {}` and `plugins/` is an empty directory (not a symlink), so `claude --print` never spawns a channel plugin that could SIGTERM the interactive session's bun.
2. Constrain output length — heartbeat trims at 3500 chars before forwarding to the notifier; prompts that ramble waste the budget.
3. Be explicit about tools — say *"no tool use"* when you want a fast pulse, or *"use `mcp__X__Y`"* when you want a query.

### `set-notifier <none|log|telegram>`

Updates `notifications.channel`. Membership check — anything else rejected.

- `none` — silent; no-op notifier.
- `log` — appends to `scripts/heartbeat/logs/notifications.log`.
- `telegram` — sends via `NOTIFY_BOT_TOKEN` / `NOTIFY_CHAT_ID` (see note in `set-prompt`).

### `set-timeout <seconds>`

Integer ≥ 10. Max timeout the heartbeat waits for `claude --print` before killing the tmux session and recording `status: timeout`.

### `set-retries <N>`

Integer 0..5. Number of retries after a failed attempt. Total attempts = `retries + 1`.

## Propagation timing

When you mutate a field, the live schedule updates in two steps:

1. `heartbeatctl reload` writes the new crontab to the workspace staging file (`scripts/heartbeat/.crontab.staging`). Instantaneous.
2. The root-privileged sync loop in `entrypoint.sh` notices the staging file differs byte-for-byte from `/etc/crontabs/agent` (`cmp -s`, not mtime — busybox `sh -nt` rounds to whole seconds and would miss same-second writes at boot) and copies it there. Runs every 15 seconds.
3. busybox crond re-scans crontab mtimes on its minute tick and picks up the new schedule. Up to 60 seconds.

**Worst case total propagation: ~75 seconds.**

The staging/sync indirection exists because busybox crond silently skips any file in `/etc/crontabs/` that isn't root-owned, so agent cannot write there directly. Entrypoint runs as root before dropping privileges, so it's the only context that can install files into `/etc/crontabs/`.

## Data files

All under `/workspace/scripts/heartbeat/` (as of v0.12.0):

Heartbeat core:

- `heartbeat.conf` — shell-sourced by `heartbeat.sh`. Regenerated by `reload`.
- `state.json` — atomic snapshot of the last run + aggregate counters. Schema `1`.
- `.crontab.staging` — written by `reload`, consumed by entrypoint sync loop.
- `logs/runs.jsonl` — append-only JSON-per-line trace. Rotated at 10MB → `.1`, `.2.gz`, `.3.gz` (max 3 generations).
- `logs/cron.log` — crond stderr for schedule-dispatch debugging.
- `logs/notifications.log` — output of the `log` notifier.
- `logs/sessions/*.log` — per-run tmux session output (last 20 retained).

Per-primitive state files (same directory):

- `identity-backup.json`, `vault-backup.json`, `config-backup.json` — hash + `last_commit` + `last_push` per backup branch. With an agent repository (046) also `memory-backup.json` and `history-backup.json`, every one of the five gains the record of its last attempt (see "State after each run" below), and `backup-dest.json` records the destination's privacy verdict.
- `.backup-<unit>.lock` (046) — the per-unit run lock of the agent-repository path.
- `token-health/<id>.json` — one per probed token, plus `token-health/warnings.jsonl` (warning audit trail).
- `qmd-index.json` — reindex state, schema `{hash, last_run, last_status, runs[, pending]}` (see "Vault RAG" below).
- `wiki-graph.json` + `.wiki-graph.lock` — wiki-graph freshness/counts state and its flock file.
- `review-prompt.txt` (037) — the effective weekly-review prompt (custom or
  the localized default), written by `reload` only when
  `features.heartbeat.review.enabled: true`; absent otherwise. `{{VAULT_DIR}}`
  and `{{WORKSPACE}}` are already substituted — this is what the crontab line
  actually `cat`s at tick time.

Per-primitive cron logs (docker mode; the cron lines written by `reload` redirect here):

- `logs/backup-identity.log`, `logs/backup-vault.log`, `logs/backup-config.log`, `logs/token-health.log`, `logs/qmd-reindex.log`, `logs/wiki-graph.log`, `logs/review.log` (037, only when the review notice is enabled), `logs/backup-memory.log` and `logs/backup-history.log` (046, only with an agent repository).
- `logs/agent-repo.log` (046) — what the work-clone helper could not do (no `GITHUB_PAT`, a non-git directory in the way, a failed creation). Not a cron log.

The qmd reindex lock is the exception to the "all under `scripts/heartbeat/`" rule: it lives at `<qmd cache root>/.reindex.lock`, shared with the first-boot setup so setup and reindex never overlap. The cache root is `$QMD_CACHE_HOME`, falling back to `~/.cache/qmd` — docker mode: `HOME=/home/agent`, which is the `.state/` bind-mount; local mode: the rendered entrypoints export `QMD_CACHE_HOME=<workspace>/.state/.cache/qmd`. Either way it persists under `.state/`.

## Backup commands

The agent's persistent state is sliced into independent orphan branches.
Where they go is resolved on every run by one rule
(`backup_dest_resolve`, `docker/scripts/lib/backup_dest.sh`):

- **an associated repository** (`backup.repo.url`, docker mode only, 046): five
  units; since 0.34.0 (048) each one is the directory `.agent-backup/<unit>/` of
  the repository's `main` branch (before, the branches `backup/identity`,
  `backup/vault`, `backup/config`, `backup/memory` and `backup/history`). New
  results: `no-main`, `main-busy` (exit 2), `main-protected` (exit 2),
  `foreign-dir` and `other-agent` for a directory of main; success keeps the 046
  text (`backup-<unit>: <sha8> pushed`), and after a verified write a marked legacy
  branch is deleted (`legacy branch backup/<unit> deleted (its backup is in main)`).
  `backup-status` adds `location`, `legacy_branch` and `repo_size_kb`;
- **else the agent's fork** (`scaffold.fork.url`): the three branches of
  before (identity, vault, config), on the pre-046 code path, with its
  messages, exit codes and state files unchanged;
- **else nothing**: each unit says so and exits `0`.

Each unit is idempotent, hash-based, and pushes nothing when its input
hasn't changed since the last commit. Restore happens via
`setup.sh --restore-from-repo <url>` (an alias of `--restore-from-fork`),
which pulls them in order: config, identity, vault, memory, history.

| Branch | Cadence (docker mode: cron lines written by `reload`) | What it stores |
|---|---|---|
| `backup/identity` | watchdog 60s + post-plugin-install + cron `30 3 * * *` (override via `features.identity_backup.schedule`; with a fork the line exists only when `features.identity_backup.enabled` is `true`, with a repository unless it is `false`) | Telegram pairing, plugin config, settings, `.claude.json`, age-encrypted `.env`. The `/login` credentials file is not in the list |
| `backup/vault` | cron `0 * * * *` (override via `vault.backup_schedule`) | Markdown subset of the vault. Excludes `.obsidian/workspace*.json`, cache, `.trash/`, `*.sync-conflict-*`. Inside `store/` when `backup.sensitive: true` (repository only) |
| `backup/config` | cron `30 3 * * *` (toggle via `features.config_backup.enabled`) | `agent.yml` (plaintext, no secrets). With a repository also `CLAUDE.md`, `personas/` (no `*.bak*`), `docker-compose.override.yml` and the workspace `.claude/` list (`settings.json`, `skills/`, `commands/`, `agents/`, `hooks/`, `output-styles/`); all but `agent.yml` in `store/` when sensitive |
| `backup/memory` (repository only) | cron `40 3 * * *` (`features.memory_backup.{enabled,schedule}`) | auto memory (plaintext, or `store/` when sensitive), the claude-mem store and the `backup.extra_paths` (always `store/`) |
| `backup/history` (repository only) | cron `50 3 * * *` (`features.history_backup.{enabled,schedule}`) | `/home/agent/.claude/projects/**` minus the `memory/` dirs, always in `store/` |

`store/` is the encrypted block store (one `age` data key per store, kept
encrypted for the operator key `backup.identity.recipient`); see
[`docs/architecture.md`](architecture.md#backup-destination-credential-and-encryption-046).
The memory and history cron lines are written only with an associated
repository, an enabled unit and a valid five-field schedule (`*` and `*/N`
are allowed in every field, the minute included, unlike the review notice);
an invalid one is omitted with
`heartbeatctl: WARN invalid features.<unit>_backup.schedule — backup-<unit> line omitted`.
With a fork or no destination the crontab is the same as before 046.

Local mode: only the **vault** backup is scheduled — as a systemd timer (`agent-<name>-vault-backup.timer`, `OnCalendar` converted from `vault.backup_schedule`). Identity and config backups have no local scheduler (no `local-*` unit templates exist for them); run them from a docker deployment or not at all. The agent repository is docker-only: in local mode `--regenerate` warns that `backup.repo` and `backup.sensitive` are ignored, and the local vault backup keeps pushing plaintext markdown to the fork.

> **Freshness check**: `agentctl doctor` verifies that each backup pushed within its expected cadence × 2 (identity 48h, vault 25h, config 8d — local mode checks vault only) and prints a humanized delta (`pushed 12h ago`); a stale or never-pushed backup is a warning (exit `1`), not a failure. Docker mode: override the thresholds for one-off runs via `DOCTOR_IDENTITY_MAX_AGE_HOURS`, `DOCTOR_VAULT_MAX_AGE_HOURS`, `DOCTOR_CONFIG_MAX_AGE_DAYS`. Local mode ignores those env vars — its vault check passes a fixed 25h. See "agentctl doctor exit contract" below. `heartbeatctl status` prints the same `last_push` timestamps for the identity, vault and config branches under their respective sections; with an agent repository, `backup-status` (below) covers all five.

### With an associated repository (046)

Every `backup-<unit>` command follows the same steps when the destination
is a repository; with a fork or no destination it runs the code of before.

1. Takes the unit's lock (`scripts/heartbeat/.backup-<unit>.lock`,
   `flock -n`). If another run holds it, the command says so, exits `0` and
   records nothing.
2. Checks that `GITHUB_PAT` is in the environment.
3. Builds the unit's list of sources and, if something must be encrypted,
   checks for the operator key (`backup.identity.recipient`).
4. Computes the unit's hash. `--dry-run` stops here and says whether it
   changed, and records nothing (also when it stops earlier, without a
   credential). Steps 2 to 4 never touch the network.
5. Checks the repository's privacy and reads its heads (below). This runs
   on every cycle, also with no changes, so a credential that stopped
   working or a deleted backup branch shows up on the next cycle.
6. If the hash and the remote head of its branch are the ones in the state,
   it ends with `no-change` without cloning, fetching or pushing.
7. Prepares its own clone cache (a branch missing on the remote starts from
   an empty cache and is born with one commit), checks the ownership mark
   `.agentic-pod-backup.json` (`{schema, agent, unit}`), builds the tree
   (plaintext files copied, encrypted ones packed into `store/`, the mark
   written), commits and pushes `refs/heads/backup/<unit>` only.
8. Writes its state, merging fields, and releases the lock.

**Privacy check.** An anonymous `git ls-remote` must be refused for lack of
a credential (it is not repeated while the verdict for the same URL stays
`private` and less than 24 hours have passed since the last anonymous
probe) and an authenticated one, with `GITHUB_PAT` through the image-baked
askpass, must succeed. The verdict lands in
`scripts/heartbeat/backup-dest.json` (`url`, `verdict`, `checked_at`,
`anon_checked_at` and their epoch twins):

| Verdict | Meaning | Pushes |
|---|---|---|
| `private` | the anonymous probe was refused for lack of a credential, the authenticated query works | yes |
| `unverified-allowed` | the anonymous probe failed for another reason, the authenticated query works, `backup.repo.allow_unverified: true` | yes |
| `unverified` | the same, without `allow_unverified` | no |
| `public` | the anonymous probe worked | no, not even with `allow_unverified` |
| `unreachable` | the authenticated query failed (credential, network, missing repository) or the URL is not `https://github.com/<owner>/<name>` | no |

**Results and messages** (`<u>` is the unit; `last_result` in the state file):

| Result | Exit | Message |
|---|---|---|
| `ok` | 0 | `backup-<u>: <8 hex> pushed`; identity appends its mode, `(full)` or `(partial)` |
| `no-change` | 0 | `backup-<u>: no changes since last backup (hash <hash>)`, or `... no changes after stage-diff (hash <hash>)` when the built tree equals the remote head |
| `nothing-to-back-up` | 0 | `backup-<u>: nothing to back up yet` |
| `no-credential` | 0 | `backup-<u>: no GITHUB_PAT in the environment - cannot push to the agent repository` |
| `no-recipient` | 0 | `backup-<u>: no encryption key (backup.identity.recipient) - nothing pushed` |
| `not-private` | 0 | `backup-<u>: the repository is public - refusing to push` |
| `unverified` | 0 | `backup-<u>: could not verify that the repository is private - refusing to push` |
| `foreign-branch` | 0 | `backup-<u>: branch backup/<u> exists and is not a launcher backup - refusing to write` |
| `other-agent` | 0 | `backup-<u>: branch backup/<u> belongs to another agent - refusing to write` |
| `unreachable` | 2 | `backup-<u>: repository unreachable (credential, network or missing repository)` |
| `push-failed` | 2 | `backup-<u>: push failed` (stderr) |
| `error` | 2 | `backup-<u>: could not build the backup (<reason>)` (stderr) |
| lock held | 0 | `backup-<u>: another run holds the lock - skipping` (no result recorded) |

Policy refusals exit `0` so cron does not treat them as errors; they stay
visible in the state file, in `backup-status` and in `agentctl doctor`.
Transient failures exit `2`, like the push failure of the fork path. Two
more lines can appear without being a result: `backup-<u>: store key
rotated (<reason>) - full upload` (stderr) when a store changes its data
key, and `backup-memory: skipping extra path '<path>' (<reason>)`. The
pre-046 early exits (`no identity files yet`, `vault not enabled`, `vault
dir ... does not exist yet`, `agent.yml missing`) keep their message and
exit `0` with any destination. A foreign or unmarked branch is fixed by
deleting it on GitHub: the next cycle recreates it.

**State after each run.** With a repository the state file gains
`last_attempt`, `last_attempt_epoch`, `last_result`, `attempt_hash` (empty
when the run ended before hashing) and, for units with a store,
`store_recipient`. `hash`, `last_commit` and `last_push` (ISO 8601 UTC,
ending in `Z`) change only on `ok`, or on a tree identical to the remote
head. A unit with something encrypted makes a small commit every time it
packs (`age` encrypts differently each time), so a freshly restored agent's
first cycle commits once without new blocks.

**Time limits** (inside the container, `timeout -k 10`): 60 s for each
privacy query (`BACKUP_PROBE_TIMEOUT_S`); 60 s for each fetch and push of
identity, vault and config (`BACKUP_GIT_TIMEOUT_S`); 900 s for those of
memory and history (`BACKUP_PUSH_TIMEOUT_S`), because after a restore they
pull the whole store. The supervisor caps its identity trigger at 300 s
with a repository (90 s with a fork) and, after a failed attempt on the same
content, waits `IDENTITY_BACKUP_RETRY_S` (900 s) before trying again; new
content triggers at once.

### `backup-identity`

Snapshot the agent's identity subset (pairing, plugin config, settings,
`.claude.json`, optionally age-encrypted `.env`) to the `backup/identity`
orphan branch. The `/login` credentials file is not part of it.

```
heartbeatctl backup-identity                       # default: run
heartbeatctl backup-identity --configure-key KEY   # set recipient + backup
heartbeatctl backup-identity --disable             # stop scheduled backups
heartbeatctl backup-identity --dry-run             # stage + diff, no push
heartbeatctl backup-identity --gc                  # git gc before push
```

Encryption uses an SSH-key recipient fetched from `github.com/<owner>.keys`
at scaffold time (the fork's owner, else the associated repository's).
Without a configured recipient, the primitive falls back to **partial
mode** — plaintext files committed, `.env.age` omitted, visible in
`heartbeatctl status`; identity therefore never ends in `no-recipient`.
With a repository it encrypts the secrets file at the workspace root
(`/workspace/.env`); with a fork it still reads `<state dir>/.env`, where a
docker agent does not keep one. Full spec at
`docs/superpowers/specs/2026-04-22-identity-backup-design.md`.

`--configure-key <path|pubkey>` takes an `ssh-ed25519` or `ssh-rsa` public
key, as a string or as a path readable **inside the container**, writes it
to `backup.identity.recipient` and runs the unit. With an associated
repository it also prints, after `recipient updated`:

```text
backup-identity: key fingerprint SHA256:<fingerprint> (<comment>)
backup-identity: encrypted units re-encrypt for this key on their next run (full upload)
```

This is how an existing agent sets its key: `--regenerate` only warns that
it is missing. Check that the fingerprint belongs to a key whose private
half you hold, or the encrypted backups cannot be restored. Changing the key
later makes every unit with a store rotate its data key and upload
everything again on its next run. With a fork or no destination the output
is the same as before 046.

`--gc` with a repository runs `git gc` on the repository-path cache under
the unit's lock (a supervisor-triggered run could be committing there), then
the unit. With the lock taken, the `gc` is skipped and the run reports the lock.

### `backup-vault`

Snapshot the markdown subset of the vault to `backup/vault`.

```
heartbeatctl backup-vault              # default: run
heartbeatctl backup-vault --dry-run    # stage + hash, no push
heartbeatctl backup-vault --gc         # git gc before push
```

The vault location comes from `vault.path` in `agent.yml` (default
`.state/.vault`, mapped to `/home/agent/.vault` inside the container by
the bind-mount). Files are filtered by `*.md` extension; the
`.obsidian/`, `.trash/`, and `*.sync-conflict-*` exclusions exist so
Syncthing-induced churn doesn't pollute the snapshots when the vault
is also synced to other devices.

Deletes propagate: the staged tree is wiped before each commit, so a
removed note drops out of the next `backup/vault` commit instead of
lingering forever. (With a store, `store/` is kept between commits so its
blocks can be reused.)

Sensitive agents (`backup.sensitive: true`): with a repository the same
files go into `store/` and the tree holds no plaintext `.md`; with a fork and
no repository the command pushes nothing and says
`backup-vault: this agent is marked as sensitive and has no agent repository - not pushing the vault in plaintext`
(exit `0`). Marking an agent sensitive removes the plaintext files from the
next commit, not from the branch history: prune the branch for that.

### `backup-config`

Snapshot `agent.yml` to `backup/config` (with a repository, also the files
listed in the table above).

```
heartbeatctl backup-config              # default: run
heartbeatctl backup-config --dry-run    # stage + hash, no push
heartbeatctl backup-config --gc         # git gc before push
```

This branch is what `setup.sh --restore-from-repo` / `--restore-from-fork`
reads first during a restore — `vault.path` and other rendered-file inputs
all live in `agent.yml`, which therefore stays in plaintext even for a
sensitive agent. Disable scheduled config backups via
`features.config_backup.enabled=false` in `agent.yml`.

With a repository, every run (whatever its result, except `--dry-run`) also
creates or repairs the agent's work clone at `/workspace/agent-repo`, so a
clone that could not be created at boot is retried daily. That step never
changes the unit's result or exit code; what it could not do goes to
`logs/agent-repo.log`.

### `backup-memory` (046)

Snapshot the auto memory, the claude-mem store and the
`backup.extra_paths` to `backup/memory`. Repository only: with a fork or no
destination it prints
`backup-memory: no agent repository in agent.yml (backup.repo.url) - nothing to back up to`
and exits `0`.

```
heartbeatctl backup-memory              # default: run
heartbeatctl backup-memory --dry-run    # hash only, no network, no push
```

- **Sources**: `/home/agent/.claude/projects/<project>/memory/**`
  (`auto-memory/<project>/...`, plaintext unless sensitive), everything
  under `/home/agent/.claude-mem/` except `logs/`, `backups/`, `run/`,
  `*.pid`, `telemetry*.json`, `*heartbeat*.json`, `*health*.json` and
  `supervisor.json` (`claude-mem/...`, always encrypted), and each
  `backup.extra_paths` entry read under `/workspace/` (`extra/<path>`, always
  encrypted). `*-wal`, `*-shm` and `*-journal` files are skipped everywhere.
- **SQLite**: every database is recognized by its header and backed up as a
  consistent copy made with SQLite's backup API, never the live file; an
  unchanged database produces no new backup.
- **Extra paths** that break the rule of `backup.extra_paths` (see the
  README) or do not exist are skipped with
  `backup-memory: skipping extra path '<path>' (<reason>)`, reason
  `not relative`, `not allowed`, `outside the workspace` or `missing`; the
  unit goes on.
- With no auto memory, no claude-mem directory and no extra path it ends in
  `nothing-to-back-up`. Without the operator key and with something to
  encrypt, in `no-recipient`.

### `backup-history` (046)

Snapshot the conversation transcripts, `/home/agent/.claude/projects/**`
minus the `memory/` directories, to `backup/history`, always encrypted.
The heartbeat's isolated config dir is not included. Repository only, with
the same message as `backup-memory` otherwise.

```
heartbeatctl backup-history             # default: run
heartbeatctl backup-history --dry-run   # hash only, no network, no push
```

Each `.jsonl` is read up to its last newline, so a line being written is
left for the next cycle. The branch mirrors the current state: what Claude
Code deletes under its 30-day retention also leaves the head of the branch
and stays only in its history. Without the operator key it ends in
`no-recipient`; with no transcripts, in `nothing-to-back-up`.

### `backup-status [--json]` (046)

Where each backup unit stands. Read-only: it never touches the network,
never modifies anything, and never prints the credential, only whether it
is present.

```
heartbeatctl backup-status              # readable summary + one row per unit
heartbeatctl backup-status --json
```

With an associated repository the JSON carries `destination` (`kind`,
`url`, `verdict`, `checked_at`, from `backup-dest.json`), `credential`
(`present` or `missing`), `sensitive`, `recipient` (`configured`, `type`,
`fingerprint`, `comment`), `extra_paths` (`declared`, `missing[]`,
`bytes`), `units[]` (`unit`, `enabled`, `last_push`, `last_attempt`,
`last_result`, `max_age_hours`, `cache_bytes`), `cache_bytes_total` and
`work_clone` (`path`, `present`, `unpublished_commits`, `dirty_files`). The
thresholds are identity 48 h, vault 25 h, config 192 h, memory 49 h and
history 49 h. `cache_bytes` is the size of the unit's clone cache, a good
approximation of what its branch takes in the repository. With a fork or no
destination it reports the destination and the three units of before, read
from their state files.

The readable form prints the same data, then a row per unit with its last
push, last result and a status: `ok`, `disabled`, `never pushed`,
`stale (>Nh)`, plus `last attempt <result>` when the last attempt did not
end in `ok` or `no-change`. `agentctl doctor` reads this JSON (see below).

## Token health

Periodically probes the free-tier auth endpoints of every configured
external token, so you find out a PAT expired *before* Claude tries to
use it and dies with a 401 mid-task.

Probes (free, no quota cost):

| Token              | Probe                                                 | Detects                |
|--------------------|-------------------------------------------------------|------------------------|
| `GITHUB_PAT`       | `GET https://api.github.com/user`                     | expired/revoked PAT    |
| `NOTIFY_BOT_TOKEN` | `GET https://api.telegram.org/bot<TOKEN>/getMe`       | revoked Telegram bot   |
| `ATLASSIAN_*_TOKEN`| `GET <jira_url>/rest/api/3/myself` (basic auth)       | expired Atlassian token|
| Claude Code OAuth  | local read of `~/.claude/.credentials.json` `expiresAt` — no network call | expired OAuth, or expiring within 30 min (early warn, so you can `/login` before the next heartbeat 401s) |

The claude_oauth probe writes `token-health/claude_oauth.json` like the
others, and maps both "expired" and "expires in <30 min" to `auth_fail`
so the same warning/dedup pipeline applies. The runner only invokes it
when `~/.claude/.credentials.json` exists (override the path with
`TH_CLAUDE_CRED_OVERRIDE`) — a never-logged-in agent gets no
`claude_oauth.json` at all rather than a `skipped` one. A file that
exists but has no parseable `expiresAt` does record `skipped`.

Firecrawl and Google Calendar are NOT probed automatically — Firecrawl
charges per call and Google's OAuth refresh path is fragile. Run a
manual probe with `agentctl heartbeat token-check` if you suspect either,
or rely on Claude's own error reporting when it hits the MCP.

### `token-check`

```
heartbeatctl token-check
agentctl heartbeat token-check          # same, from the host (docker mode only)
```

Local mode has no token-health scheduler and `agentctl heartbeat
token-check` exits `2` there — token health is a docker-mode feature.

Triggers a one-shot probe of all configured tokens. In docker mode an
hourly cron line does the same automatically (default schedule
`0 * * * *`). State files land
in `<workspace>/scripts/heartbeat/token-health/<id>.json`:

```json
{
  "id": "github",
  "kind": "github_pat",
  "last_check": "2026-05-02T22:00:00Z",
  "status": "ok",
  "http_code": "200",
  "latency_ms": 142,
  "consecutive_failures": 0,
  "first_failure_at": null,
  "last_warned_at": null,
  "error": null
}
```

`status` ∈ `{ok, auth_fail, network, skipped}`. Only `auth_fail` and
sustained `network` failures emit warnings — the docker-mode `agentctl doctor`
adds checks 16-18, which read the same files (github, telegram, every
`atlassian-*`, and `claude_oauth` when present) and surface them as `✗`/`⚠`. A
probe file older than `DOCTOR_TOKEN_MAX_AGE_HOURS` (default `2`) is itself a
warning — a dead cron is as bad as a dead token.

### Warnings

When a token transitions from `ok` → `auth_fail`, the runner emits ONE
warning through the configured heartbeat notifier (Telegram if set,
log otherwise). The same warning re-fires every 24h if the failure
persists, so the user gets a daily reminder without spam. Recovery
(`auth_fail` → `ok`) emits a single "recovered" notice.

Warning history is appended to
`<workspace>/scripts/heartbeat/token-health/warnings.jsonl` regardless
of the notifier outcome, so the audit trail survives a broken Telegram
channel.

### Disable / tune

```yaml
# agent.yml
features:
  token_health:
    enabled: false        # opt out entirely
    schedule: "*/15 * * * *"   # custom cron, default "0 * * * *"
```

Override the dedup window per-invocation: `TH_DEDUP_SECS=3600
heartbeatctl token-check` (default 86400 = 24h).

- `0` — success
- `1` — validation error (bad input value, unknown schema)
- `2` — operational error (filesystem, yq, missing state.json)

## Vault RAG

### `qmd-reindex [--dry-run]`

```
heartbeatctl qmd-reindex                # docker mode, in-container
agentctl heartbeat qmd-reindex         # both modes, from the host
```

Reindexes the vault's QMD semantic search (feature 010; local parity 013).
Opt-in: requires **both** `vault.enabled: true` and `vault.qmd.enabled: true`
in `agent.yml`. Fail-silent — the run path always exits `0` (a cron/watcher
tick must never crash); honesty is in the state file.

Two schedulers invoke the same command:

- Docker mode: a cron backstop, default `*/5 * * * *` (override via
  `vault.qmd.schedule`), plus the inotify watcher (`qmd_watch.sh`, started by
  `start_services.sh`) on vault changes.
- Local mode: the `agent-<name>-qmd-reindex.timer` systemd unit (`OnCalendar`
  converted from `vault.qmd.schedule`; a non-convertible schedule falls back to
  the feature default and drops a `qmd-schedule.fallback` marker that `doctor`
  warns about) plus the `agent-<name>-qmd-watch.service` watcher.

Overlap is safe: the critical section is `flock`-guarded
(`<qmd cache root>/.reindex.lock`, shared with the first-boot setup) and
hash-debounced (`vault_hash` over the markdown subset — the same hash the vault
backup uses).

`--dry-run` (docker mode): resolve + hash + report whether a run would reindex;
no embed, no state write. The local wrapper has no dry-run mode, so
`agentctl heartbeat qmd-reindex --dry-run` is refused in local mode (exit `2`)
rather than silently running a real reindex.

### `qmd-migrate [--dry-run|--force]` (037)

```
heartbeatctl qmd-migrate                # docker mode, in-container
agentctl heartbeat qmd-migrate         # both modes, from the host
```

One-time move of the search collection from the legacy `**/*.md` mask to
`wiki/**/*.md`. Runs **automatically** on the first `qmd-reindex` tick after
an agent upgrades to 037 — this subcommand is the manual check/trigger, not
the only way it happens.

- No flags: idempotent. If the layout sentinel is present, prints "already
  migrated" and exits `0` without touching qmd at all.
- `--dry-run`: prints the current state (`collection=<layout>
  migration=<state>`) and the six steps (`remove`, `add` with the new mask,
  `update`, write the sentinel, `cleanup`, `embed` if pending) — runs nothing.
  Safe in **both** modes, unlike `qmd-reindex --dry-run`.
- `--force`: recreates the collection with the `wiki/` mask even if already
  migrated — for repairing a stale sentinel or after a manual `cleanup`.

`remove`+`add` reuses embeddings (qmd keys vectors by content hash, not by
collection), so migrating is fast and never re-downloads or re-embeds
unchanged content. `status`/`doctor` in both modes report
`collection=<layout> migration=<state>`, computed live from the sentinel and
`index.sqlite` — this is visible even before the first reindex tick runs.

#### Embed completion loop (018)

A single `qmd embed` runs inside an engine session hard-capped at ~30 minutes;
on a large first-time corpus one pass dies with "LLM session expired", leaving
part of the corpus without vectors. As of v0.12.0 the reindex runs successive
fresh `qmd embed` passes inside one locked invocation until one of:

- **complete** — a pass prints `All content hashes already have embeddings`,
  or `qmd status` reports `Pending: 0` → `last_status: indexed`, `pending: 0`.
- **stalled** — pending did not decrease between consecutive passes
  (permanently-failing documents) → `last_status: stalled`, pending persisted.
- **pass cap** — `QMD_EMBED_MAX_PASSES` reached (fixed constant, `12` as of
  v0.12.0; env-overridable for tests only — deliberately **not** an `agent.yml`
  field) → `last_status: partial`, `pending` = the last count parsed from
  `qmd status` (`0` if no pass ever produced a parseable count).
- **pass failure/timeout** → `last_status: error`, and the *previous* hash is
  kept so the next tick re-runs `update` from scratch. `pending` is carried
  over from the prior state file unchanged (including its absence).

#### `qmd-index.json` state schema

```json
{
  "hash": "<sha256 over vault markdown content + filenames>",
  "last_run": "2026-07-12T18:00:00Z",
  "last_status": "indexed",
  "runs": 42,
  "pending": 0
}
```

- `last_status` ∈ `{indexed, skipped, error, partial, stalled}`.
- `pending` — documents still needing an embedding, parsed from `qmd status`
  (`Pending: N`). Absent on pre-018 state files, which readers treat as
  *unknown*, never as zero.
- `runs` increments on every state write, regardless of status.

Resume guarantee (018): the unchanged-vault guard skips embedding **only** when
the hash is unchanged *and* `pending == 0` (then writes `skipped`). An
unchanged vault with `pending > 0` — or with `pending` unknown — resumes the
embed loop without re-running `update`. A `partial` or `stalled` first index
therefore self-heals on subsequent ticks even when the vault never changes.

Local mode: `agentctl doctor` degrades to a warning when `last_status` is
`error`; `partial` and `stalled` are reported as a **pass** line with the status
in parentheses (as of v0.12.0 — they are self-healing states, not failures), and
`agentctl status` shows the index presence, the last-reindex timestamp and its
status. See "agentctl doctor exit contract" below.

### `wiki-graph`

```
heartbeatctl wiki-graph
agentctl heartbeat wiki-graph           # same, from the host (both modes)
```

Regenerates the derived wiki graph + structural lint (feature 014). Reads the
whole `wiki/` and writes five artifacts under `<vault>/.graph/`:
`graph.json`, `backlinks.json`, `findings.json` (structural lint plus, as of
037, the PARA actionability queue — see below), `policy.json` (037: effective
review cadences, archive threshold, qmd collection layout) and `packets.json`
(037: every page with a valid `packet:` value). Plus the
`<workspace>/scripts/heartbeat/wiki-graph.json` state file (freshness +
counts). `flock`-guarded (lock lives under `scripts/heartbeat/`, never in the
vault), fail-silent (always exits 0; honesty is in the state file). NEVER edits the
wiki — it reports; the agent fixes. A `20 */6 * * *` backstop runs the same command
(docker mode: cron line; local mode: the `agent-<name>-wiki-graph.timer` unit;
override via `vault.wiki_graph.schedule`); opt out with
`vault.wiki_graph.enabled=false`.

**The PARA review queue (037):** `findings.json` and `wiki-graph.json.counts`
gain seven kinds beyond the pre-037 structural set —
`project_incomplete`, `project_overdue`, `review_due`, `pending_ingest`,
`description_missing`, `problem_unfed`, `archive_candidate` — plus
`schema_delta_pending` (the schema delta self-denounces if an existing vault
never integrated it). These are deterministic, computed by the same awk+jq
runner, never by an LLM.

Local mode: `agentctl status`/`doctor` surface the freshness, the seven queue
counters (`review_due=<n> project_overdue=<n> project_incomplete=<n>
pending_ingest=<n> archive_candidate=<n> schema_delta_pending=<n>
problem_unfed=<n>`, in that fixed order — informative only, never a warn) and
degrade on integrity findings (broken links, frontmatter violations, index
drift → warn) or a dead runner (fail). Docker mode (as of 037):
`heartbeatctl status` prints a `wiki-graph: <status> @ <last_run> —
due=<n> overdue=<n> incomplete=<n> ingest=<n> archive=<n> delta=<n>
unfed=<n>` line (same seven counters, same order) whenever
`wiki-graph.json` exists, alongside the existing `qmd index:` line;
`agentctl doctor` still has no wiki-graph checks in docker mode — read
`scripts/heartbeat/wiki-graph.json` directly there. See "agentctl doctor
exit contract" below.

### Review notice (opt-in, docker only, 037)

A **separate** heartbeat tick, distinct from the main interval, that reports
the PARA queue above without acting on it. Off by default — enable with
`features.heartbeat.review.enabled: true` in `agent.yml`, then `reload`.

```yaml
features:
  heartbeat:
    review:
      enabled: true
      schedule: "7 9 * * 1"   # default: Monday 09:07
      prompt: ""               # empty = localized default (mixed -> Spanish)
```

- **Pick a minute that is not a multiple of your heartbeat interval.** The
  minute field deliberately rejects `*` and `*/N` (`_v_cron5`, image-baked) —
  a review notice firing on every tick would defeat "at most one notice a
  week" (SC-007). The default `7` avoids every common interval (5, 10, 15,
  30, 60).
- An invalid schedule WARNs to the boot log naming
  `features.heartbeat.review.schedule` (never the value) and the crontab line
  is simply omitted — the rest of `reload` proceeds normally.
- The effective prompt (custom or the localized default, `{{VAULT_DIR}}` and
  `{{WORKSPACE}}` already substituted) is written to
  `scripts/heartbeat/review-prompt.txt` and `cat`'d into the crontab line at
  tick time — see "Data files" above.
- The tick uses the SAME isolated heartbeat session as a regular tick
  (`trigger: "review"` in `runs.jsonl`), runs independently of
  `features.heartbeat.enabled` (a paused main heartbeat still gets its review
  tick), and is subject to the same collision rule as any two ticks: if one
  is still running when the other's minute arrives, the loser is `skipped`,
  never queued.
- Local mode: no timer ships for this — the queue is still readable via
  `wiki-graph.json`/`findings.json`, or offered to the human at the start of
  a conversation per the vault's own `CLAUDE.md` protocol.

## agentctl doctor exit contract

Not a heartbeatctl subcommand, but the consumer of most state files documented
above. `agentctl doctor` aggregates pass/warn/fail checks and exits (both
modes, as of v0.12.0):

- `0` — all checks passed
- `1` — warnings only
- `2` — at least one failure

Checks over this CLI's surface:

| Check | Degrades to | Mode |
|---|---|---|
| Backup never pushed / stale (identity 48h, vault 25h, config 8d) | warn | docker (vault only in local) |
| With an agent repository (046): a unit never pushed, stale (memory and history 49h) or whose last attempt failed; a verdict other than `private` / `unverified-allowed`; `GITHUB_PAT` missing; no encryption key; an extra path missing; the work clone missing or with unpublished commits / uncommitted files; backup caches above 800 MB (`DOCTOR_BACKUP_CACHE_MAX_MB`) | warn | docker |
| Token probe `auth_fail` (incl. claude_oauth expired or expiring <30 min) | fail | docker |
| Token probe `network` failure, missing or stale probe file | warn | docker |
| QMD index not built yet | warn | local |
| QMD last reindex `last_status: error` | warn | local |
| QMD watcher unit failed (timer still backstops) | warn | local |
| QMD / wiki-graph schedule fallback marker present | warn | local |
| wiki-graph integrity findings (broken links, frontmatter violations, index drift) | warn | local |
| wiki-graph runner dead (last run older than 2x the schedule interval) | fail | local |
| D1 — workspace `.env` missing, or not mode `0600` | warn | local |
| D2 — a secret referenced by `.mcp.json` is absent from `.env` | warn | local |
| D3 — the INSTALLED unit does not load the workspace `.env` | warn | local |
| D4 — `.env` fails the portable-subset lint (BOM, trailing backslash, bad key) | warn | local |
| An unconsumed `exited` verdict sits next to a live session pointer | warn | local |
| The installed unit does not run the 022 session hooks | warn | local |

Rows D1-D4 are 021 (local secret delivery); they never fail, only warn — a
missing secret degrades one MCP, and refusing to start the agent over it would
trade a partial outage for a total one. D3 reads `systemctl show -p
EnvironmentFiles`, **not** `systemctl cat`, which returns *Permission denied* on
a root-only unit and made the check skip itself in silence (caught on live
hardware, 2026-07-18).

The last two rows are 022 (local session lifecycle). What is NOT there matters as
much: the doctor used to grep the journal for `session url|connected|polling` as
a liveness signal. That check was **removed** — a healthy `--spawn=session` agent
is silent in the journal, so it cried wolf on every healthy agent. During the
measured incident every conventional signal was green (`is-active`, zero
restarts, no journal errors, an ESTABLISHED socket with real bidirectional
traffic) while the agent was unreachable, which is why the surviving checks
inspect the pointer and the recorded exit cause instead of the network.

The QMD and wiki-graph rows are checked by the local-mode doctor only: as of
v0.12.0 the docker-mode doctor has no qmd/wiki-graph checks (its RAG-adjacent
coverage is the vault-skeleton check plus the backup-freshness checks: three
with a fork, five with an agent repository).

With an agent repository the docker doctor takes its backup data from
`docker exec -u agent <agent> heartbeatctl backup-status --json`; if that
command fails while the container runs, it falls back to reading the five
state files. Without a repository its backup output is the same as before
046.
`last_status: partial` / `stalled` do not degrade the exit code in either mode —
only `error` does.
